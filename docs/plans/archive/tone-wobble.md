# ツマミを上げたときの音の揺れと、音量の低下を直す

## 目的・背景

2026-11-19 にユーザーが報告した。

- Treble を上げると、音が揺れるように感じる
- Bass を上げると、全体の音量が下がる
- 出力は Bluetooth の骨伝導のヘッドホン（低音が出にくい）

## 見立て（未確認）

上げた分で音がデジタルの上限（0 dBFS）を超え、Windows の音のエンジンのリミッターが全体の音量を自動で下げている。

- いまの曲の多くは、もとから上限いっぱいの音量で作られている。そこへ +20 dB（振幅で 10 倍）を足すと、上げた帯域の音が上限を大きく超える
- この APO は MFX の段にあり、その後ろに Windows のリミッターがある。リミッターは上限を超えた分だけ、全部の帯域の音量をまとめて下げる
- Bass: 上げた低音はヘッドホンから聞こえないが、信号の中では大きくなっている。リミッターが全体を下げるので、聞こえる帯域の音量だけが下がって聞こえる
- Treble: 高音の大きさは曲の中で刻々と変わる。それに合わせてリミッターの下げ幅が動くので、全体の音量が揺れて聞こえる
- 当初考えた原因（フィルタの係数を一度に切り替えている、設定を見るのが 250 ms ごと）は、回している間だけの現象で、上げたあと続く揺れは説明できない

## 対応方針

### Step 1: 見立てを確かめる

- 耳で: Treble を揺れる位置まで上げたまま、Volume のツマミを 30% ほどまで下げる。揺れが消えれば、上限を超えていることが原因（Volume はこの APO の中で、リミッターの前に効く）
- 数字で（必要なら）: APO の出力の最大値を測ってログに書く

### Step 2: 直し方を決める

候補:

- A. 上げた分だけ全体を自動で下げる（+6 dB 上げたら全体を −6 dB）。音は割れず、揺れない。上げるほど全体が小さくなるので、Windows やヘッドホン側の音量を上げて補う。イコライザーで一般的なやり方
- B. 何もしない代わりに、上限を超えたことを画面に表示する（超えたら Volume を下げてもらう）
- C. A を既定にして、切り替えられるようにする

### Step 3: 実装して確かめる

## 影響範囲

- `apo/src/Dsp.*`（全体の音量の計算）、場合により画面
- DLL を変えるときは、ユーザーに管理者で入れ替えてもらう

## テスト方針

- 単体テスト: 上限いっぱいの入力に対して、出力が上限を超えないこと
- sx360: 耳で、揺れと音量の低下が無くなったことを確かめる

## 結果（2026-11-19）

- Step 1: ユーザーが耳で確かめた。Treble を上げて揺れる状態で Volume のツマミを下げると、揺れが消えた。見立てどおり、上限を超えた音を Windows のリミッターが下げていた
- Step 2: 候補 A（上げた分だけ全体を自動で下げる）にした
- Step 3: 画面のアプリが、設定ファイルに `preamp` を書くようにした。値は Treble と Bass のうち大きく上げているほうの分だけマイナス（両方とも上げていなければ 0）。APO は前から `preamp` を読めるので、DLL は変えていない
  - 単体テストを足した（`lowers_everything_by_the_largest_boost`）
  - 耳での確認はユーザー待ち
- 残る制約: Volume を 100% より上げた分は、自動では下げない（上げるための機能なので）。大きい音の曲では、リミッターが働いて揺れることがある

## 調査: 全体の音量が小さくなりすぎる問題の、根本的な解決方法（2026-11-19）

ユーザーの報告: Bass も Treble も上げると、全体の音量がものすごく小さくなる（いまは、上げた分と同じだけ全体を下げている。両方 +20 dB なら −20 dB = 音の大きさで 1/10）。

### 前提: 変えられないこと

- デジタルの音には上限（0 dBFS）がある。もとの音が上限いっぱいなら、ある帯域を上げるには、ほかを下げるか、上限を超えた分をどこかで抑えるしかない
- ハードウェアのアンプで同じ問題が目立たないのは、トーンコントロールのあとに音量のツマミとアンプがあり、ふだんは音量を絞って使っているので余裕があるため

### 試算: 実際にはどれだけ上限を超えるか

音楽の平均的な傾きに近い信号（ピンクノイズ）に、このアプリと同じフィルタをかけて、ピークの上がり幅を測った。

| 設定 | ピークの上がり幅 | いま下げている量 |
| --- | --- | --- |
| Bass +10 dB | +5.1 dB | 10 dB |
| Bass +20 dB | +13.7 dB | 20 dB |
| Treble +10 dB | +4.2 dB | 10 dB |
| Treble +20 dB | +11.9 dB | 20 dB |
| 両方 +10 dB | +6.8 dB | 10 dB |
| 両方 +20 dB | +15.6 dB | 20 dB |

- いまの下げ方は「全部の音が上げた帯域にある」という最悪の場合に合わせていて、実際に要る量より 5〜8 dB 多い
- ピンクノイズでの試算であり、曲によって変わる。低音の多い曲は Bass でもっと上がり、高音の少ない曲は Treble でもっと小さい

### 解決方法の候補

| 案 | 内容 | 音量の低下 | 作る量 | 弱点 |
| --- | --- | --- | --- | --- |
| A. 下げる量を、実際に要る量に減らす | 試算に合わせた式にする（上げた量の 6〜7 割） | 3〜4 割減る | 小（画面だけ） | 低音の多い曲などで、ときどき上限を超えて Windows のリミッターが働く |
| B. 上げた帯域だけを抑えるリミッター | 上げた帯域が大きいときだけ、その帯域の上げ幅を自動で減らす。小さい音のときはしっかり上がる | ほぼ無い | 大（APO に帯域別のリミッター） | 大きい音の場面では上げ幅が減る。作り込みと調整が要る |
| C. 自前のリミッター（先読み付き） | 上限を超える瞬間だけ全体を下げる。Windows のリミッターより前で、自分で調整したものを使う | 平均では小さい | 中（APO） | 超える量が大きいと、Windows のリミッターと同じく揺れる。単独では解決にならない |
| D. 実際の出力を測って、要る分だけ下げる | 再生中の音のピークを測り、下げる量をゆっくり合わせる | 曲に合わせた最小限 | 中（APO） | 曲や場面で全体の音量が動く |
| E. 下げた分を、出力側の音量で補う | 全体を下げた分だけ、Windows（ヘッドホン）側の音量を自動で上げる。アンプと同じ考え方 | 無い（出力側に余裕がある間） | 中 | Windows の音量を勝手に動かす。出力側が最大なら効かない。切ったときに戻し忘れると大きな音が出る。音量がリミッターの後ろで効くかはデバイスによる（未確認） |
| F. 上げられる幅を狭くする | ±20 dB を ±10〜12 dB に戻す（ハードウェアのアンプは ±10 dB 前後） | 幅が狭い分だけ小さい | 小 | 大きく効かせられない |

- B は、小型のスピーカーやスマートフォンが低音を強めるときに使っている方法（帯域別のコンプレッサー / リミッター）
- A と C の組み合わせ（少なめに下げ、まれに超えた分はリミッターで抑える）は、イコライザーのソフトで一般的
- 骨伝導のヘッドホンで Bass を上げる場合、上げた低音は聞こえないのに余裕だけを使う。低音の代わりにその倍音を足して低音があるように感じさせる方法（小型スピーカー向けの技術）もあるが、作る量は大きい

### すすめる順番

1. **A を先に試す。** 画面のアプリだけの変更で、すぐ聞いて確かめられる。両方 +20 dB のときの低下が 20 dB から 15 dB 前後になる
2. それでも足りなければ **B**。音量の低下をほぼ無くせる、根本的な方法。APO の変更（DLL の入れ替え）が要る
3. E は、音量を勝手に動かす危険があるので、すすめない

## 実装: 上げた帯域だけを抑える（案 B）（2026-11-20）

ユーザーが「B まで作る」と決めた。A（下げる量を減らす）は挟まず、B を作った。

### 作り

- APO の設定に `limit=1` を足した。付いているとき、上げているバンド（増減がプラスのもの）の上げ幅を、出力が上限（0.98）を超えない範囲に自動で抑える
- 抑えるバンドは同じ入力に並べてかけ、出力を「入力 + 割合 x（各フィルタの出力 − 入力 の合計）」で作る。割合は 0〜1 で、1 なら設定どおり
  - 出力が上限を超えそうな瞬間に、割合をすぐ下げる。そのあと 250 ms の時定数で 1 へ戻す
  - 入力が上限以下なら、出力も必ず上限以下になる
  - 割合は Bass と Treble で共通。順番にかける形も試したが、先のバンドが余裕を使い切って、後のバンドがほとんど上がらなかった
- 下げているバンドと、`limit` が無いときの動きは、前と同じ
- 画面のアプリは、いつも `limit=1` を書く。全体を先に下げる量（`preamp`）は 0 にした（`STATIC_HEADROOM_CAP_DB`）

### 試算（上限いっぱいの音量の、音楽に近い信号。両方 +20 dB）

| 全体を先に下げる量 | 場面 | 低音 | 中音（全体の音量） | 高音 |
| --- | --- | --- | --- | --- |
| 0 dB（採用） | 大きい場面 | +6.9 dB | −0.2 dB | +7.8 dB |
| 0 dB（採用） | 小さい場面（−12 dB） | +17.6 dB | −0.5 dB | +17.9 dB |
| −6 dB | 大きい場面 | +7.3 dB | −6.4 dB | +7.8 dB |
| −6 dB | 小さい場面 | +12.6 dB | −6.5 dB | +12.8 dB |

- 全体の音量は下がらない。代わりに、上限いっぱいの大きい場面では、上げ幅が +20 dB から +7 dB 前後に減る。小さい場面ではほぼ設定どおり上がる
- 全体を先に 6 dB 下げると、大きい場面での「ほかの帯域との差」は約 14 dB に増える。全体が小さくなるのと引き換え。`STATIC_HEADROOM_CAP_DB` で変えられる（画面のアプリだけの変更で済む）
- Volume を 100% より上げて入力が上限を超えた場合は、上げ幅を 0 にするだけで、超えた分は抑えない（Windows のリミッターが働く）

### テスト

- 単体テスト（`TestLimitBoost`）: 小さい音は設定どおり上がる、上限いっぱいの低音でも出力が上限を超えない、両方 +20 dB の雑音でも超えない、大きい中音は下がらない、下げているバンドは影響を受けない、大きい音が終われば上げ幅が戻る
